# DESIGN.md — LUMINA

## Components

I write the code and deploy it for three pieces: the gateway, the agent service and the worker. The web UI is provided, so I only deploy it, and I am careful not to change it, as the contract says. During development I run everything on my laptop. Once everything is ready, Vercel hosts the UI and Fly.io hosts the other three: the gateway is public, but the agent service and the worker are private. The agent service and the worker run in the same Fly app but in separate processes, so while the worker is processing a long PDF, it does not freeze the answers other users are asking for at the same time. I make the agent service private because it holds every API key and enforces the cap on deep search. If it were public, users would not have to go through the gateway and could call the agent directly; there would be no control over the rate limit or the cap, and spending could not be controlled. I rent MongoDB Atlas and set up the account, indexes and collections myself. It holds the cache, the run logs, and the documents and chunks from uploads. The cache stops me repeating a search and paying Tavily twice for the same question. It also holds the jobs collection: the upload route adds a pending job, and the worker picks that job up. Claude Sonnet 5 writes the answers, and an OpenAI model does text embedding, which means turning a chunk of text into a vector representation so memories and document chunks can be searched by meaning. Finally, Tavily supports the web search.

## Responsibilities

The browser (the UI) is where we show things to the user and where the user sends requests. It must not hold any keys or call the agent directly. The gateway talks to the browser, checks the user id, rate-limits each user, creates the request id and serves the UI. It must not hold any API keys or call Claude, the OpenAI model or Tavily search directly. The agent service is the one that holds the API keys, runs the loop and chooses the tools, decides the depth limits and the daily cap for deep search, and writes the run logs. It must not be reachable from the internet directly, and it must not upgrade a quick request to deep. The worker reads uploaded files, chunks them, embeds them and marks them indexed. It must never answer user questions or run inside the agent's process, since that would freeze the answers. MongoDB is the data source; it does not make any decisions: the code decides and MongoDB stores.

There are two caps, and they live in different places. The first is the rate limit in the gateway, which protects against too many requests, for example one user sending 100 requests a minute. The second is the deep daily cap in the agent service, which protects money, because it controls API calls and those cost money. It sits in the agent beside the API keys, because if anyone could go around the gateway, they could call the APIs and spend money. We also check every request twice. The first check is in the gateway, to reject bad input early, which is cheap. The second is in the agent itself, because we cannot assume every request came through the gateway; it costs one line with the same schema. Finally, the server must never upgrade a quick request to deep, because deep costs more money and the server would be spending money the user never agreed to, with no limit. The user is the one who chooses deep. This is a red line and an automatic fail.

## Communication

The agent talks to the browser through the gateway, using HTTP and SSE: normal HTTP for most routes, and SSE for the ask route, so the answer streams. The gateway talks to the agent over HTTP on Fly.io's private network, and it passes the SSE stream through without changing it. The agent talks to MongoDB through the MongoDB driver, which keeps one shared connection pool that is reused across requests. The agent talks to Claude, the OpenAI model and Tavily with HTTP calls to their APIs. Finally, the upload route and the worker never talk directly: the upload route writes a job row in MongoDB, and the worker reads it.

When the agent is down, the gateway cannot reach it and returns a 502, an honest error, never a fake answer. When Claude or Tavily is down, the run stops, terminated is "error", and again the user gets a 502; it never pretends it found nothing. When MongoDB is down, /health reports that the database is down, and requests that need data fail with an error. And if the worker is down, the upload still succeeds: the document waits as pending until the worker comes back, and nothing is lost. The upload route and the worker are separated, so neither needs the other to be running. If the worker crashes mid-job, the job row is still in MongoDB, so a restarted worker finds it and continues. We could run two workers later to go faster without changing the upload route at all.

The worker polls every 2 seconds, which is simple, easy to debug, and recovers from crashes on its own. For provider errors, we retry briefly and then fail loud: the SDK retries the model call a couple of times, and if it still fails, the report is an honest failure, a 502 with terminated "error". Finally, when the user closes the app, nobody is reading, so continuing would waste money, especially on a deep search. The agent stops, but it still writes the run log and records the run honestly, with terminated "error" and the message "client disconnected".

## State

Some of our data is the only copy of the truth: threads, messages, memories, spaces, documents and the files uploaded to GridFS. If we lose these, they are gone. Chunks are different, because we make them from the files in GridFS. If we delete all the chunks, we can run the jobs again and get them back; it costs us the embedding calls again, but nothing is lost. The search cache is only there to save money and time. It lives in MongoDB and also as a small copy in the agent's memory, and it deletes itself after 6 hours, so losing it only means paying Tavily again. MongoDB only clears old rows about once a minute, so our code also checks expiresAt before using a cached result. Jobs are a work queue: short-lived rows that tell the worker what to do next. Requests and runs are logs of every request and answer, and the graders read them.

There is a gap between saving a chunk and being able to find it. MongoDB saves the chunk right away, but the search index needs a few more seconds to catch up. So a document can be saved and still not show up in a search. To handle this, the worker does a read-your-write probe: before it marks a document indexed, it searches for one of the chunks it just saved, and it only changes the status when that chunk comes back. Until then the document shows embedding with a percentage, which is the truth. Without the probe, a user could ask about a document that says ready and get nothing back, and we would have no error to see.

We made three choices about state. Questions about today, the latest news or the current year skip the cache, because they should never get results that are hours old. Only the last 6 messages of a thread are sent to Claude, so follow-up questions still work but long threads don't get slower and more expensive; the full thread is still saved in MongoDB. And we count deep searches for the daily cap from the runs collection, because the runs are already saved there. That way there is only one source of truth, the count survives a restart, and /stats always matches, while a separate counter could slowly drift away from the real number.

## Trade-offs

We made four decisions that another engineer could have made differently.

First, we use Atlas Vector Search instead of a separate vector database like Pinecone or Qdrant. The good part is that a chunk's embedding is in the same document as its text and page number, so a citation is just one read, we don't have a second system to keep in sync, and filtering by Space is a normal database filter. What we give up is room to grow: the free M0 cluster allows exactly 3 search indexes and we already use all 3, it only has 512 MB, and it is a general database, not a search specialist.

Second, we use MongoDB as our job queue instead of Redis or a queue service. We don't have anything extra to run or pay for, a worker claims a job with one atomic update so two workers never take the same job, and a crash does not lose anything. But real queue services come with retries, back-off and a place for jobs that keep failing. With MongoDB we have to write the sweeper ourselves, and the worker has to poll every 2 seconds instead of being told right away.

Third, deep search runs its sub-questions in parallel, each one as its own isolated subagent with its own context. This makes a deep search much faster, because the total time is close to the slowest sub-question instead of all of them added together, and each subagent only sees its own sub-question, so its context stays small and focused. What we give up is simplicity. The code is harder, we need a limit on how many run at once so we don't hit rate limits from Claude or Tavily, the trace steps come back mixed together so every step needs its subQuestion tag, and merging the sources into one citation numbering has to wait until everything finishes.

Fourth, we combine the keyword search and the meaning search with RRF, without a re-ranker. RRF is free and instant and needs no extra model call, which helps with cost and speed. A re-ranker would read each chunk against the question and order them better, so without it a good chunk can end up at position 7 and miss the top 5. This is the one I am not sure about. I don't know yet whether recall@5 will reach 0.70 without a re-ranker, and I will only know when the benchmark runs. If it falls short, adding a re-ranker is the first thing I will try.
